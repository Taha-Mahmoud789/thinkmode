Kubernetes has a reputation problem: everyone's first week involves YAML archaeology and a CrashLoopBackOff at midnight. It does not have to be that way. Most developers need a surprisingly small subset of Kubernetes — understood deeply rather than broadly.

## The objects that matter

Ninety percent of daily work touches five object types:

```text
Pod        → smallest unit: one or more containers sharing network/storage
Deployment → declares desired pod count + rollout strategy
Service    → stable internal DNS + load balancing across pods
Ingress    → HTTP routing from outside world → services
ConfigMap  → configuration injected as env/files (secrets via Secret)
```

Everything else — StatefulSets, DaemonSets, operators — solves specific problems you will recognize when you meet them. Start here.

## A deployment that teaches the model

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
spec:
  replicas: 3
  selector:
    matchLabels: { app: api }
  template:
    metadata:
      labels: { app: api }
    spec:
      containers:
        - name: api
          image: ghcr.io/acme/api:1.42.0
          ports: [{ containerPort: 8080 }]
          resources:
            requests: { cpu: "100m", memory: "128Mi" }
            limits: { cpu: "500m", memory: "512Mi" }
          readinessProbe:
            httpGet: { path: /healthz, port: 8080 }
            initialDelaySeconds: 3
          livenessProbe:
            httpGet: { path: /healthz, port: 8080 }
            periodSeconds: 10
```

Read it as policy, not configuration:

- **Replicas + selector:** "keep exactly 3 healthy copies running." A node dies; the controller notices and replaces them. Nobody gets paged for node death anymore.
- **Resources:** requests are what scheduling promises you; limits are where the kernel starts killing. Set both honestly — OOMKilled loops are almost always lying limits.
- **Probes:** readiness gates traffic ("can I serve?"), liveness triggers restarts ("am I stuck?"). Confusing them causes most self-inflicted outages: a liveness probe hitting a dependency that blips will restart-loop a healthy pod.

## Rollouts: the feature that pays for the complexity

```bash
kubectl set image deploy/api api=ghcr.io/acme/api:1.43.0
kubectl rollout status deploy/api      # watch it happen safely
kubectl rollout undo deploy/api        # one-command rollback
```

That rollback command deploys the previous ReplicaSet's image across pods in seconds. Once a team internalizes "deploys are boring and reversible," deployment frequency stops being scary — which changes architecture decisions upstream, too.

## Debugging: four commands cover the field

```bash
kubectl get pods -o wide                  # what exists and its state
kubectl logs deploy/api --previous        # why the last container died
kubectl describe pod <pod>                # events: scheduling/probe failures explained
kubectl exec -it <pod> -- sh              # shell inside (if image allows)
```

<Callout variant="tip" title="Events before theories">
`describe pod` prints an Events section that names the actual failure — ImagePullBackOff means wrong tag or private registry auth; OOMKilled means raise memory limits; probe failures give the exact path that failed. Read events first; theorize second.
</Callout>

## When NOT to use Kubernetes

Intellectual honesty improves engineering judgment:

- **One service, one database, low traffic:** a VM with systemd is cheaper, simpler, and defensible.
- **Heavy stateful data systems:** managed databases beat self-run StatefulSets nearly always.
- **Team of two without platform experience:** PlatformFly/PaaS products deliver 90 percent of the benefit at 5 percent of the complexity.

Kubernetes earns its cost when you have many services, heterogeneous scaling needs, and either a platform team or appetite to become one. Arriving there early is how clusters become haunted.

## The survival kit

Learn the five objects deeply. Write honest resource requests. Separate readiness from liveness. Internalize rollouts and rollbacks. Read events before theorizing. And keep the exit question handy: "would a PaaS do this better today?" — because sometimes the answer is yes, and knowing that is also cloud-native maturity.
