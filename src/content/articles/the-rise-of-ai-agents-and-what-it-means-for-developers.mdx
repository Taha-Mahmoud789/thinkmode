Two years ago, an "AI agent" was a demo that could order a pizza badly. Today, agents review pull requests, triage incidents, migrate legacy codebases, and negotiate between microservices. The shift happened faster than most platform teams could write policy for it — and it changes what "being a developer" means in very concrete ways.

This article is not hype. It is a field report: how these systems actually work, where they fail, and how to position yourself and your stack for a world where software partially writes itself.

## What exactly is an agent?

A language model on its own can only do one thing: predict the next token. An **agent** wraps that model in a loop with three extra ingredients:

1. **Tools** — functions the model can call: search, run code, query a database, deploy a service.
2. **Memory** — state that persists beyond a single context window, from scratchpads to vector stores.
3. **A planning policy** — some strategy for decomposing a goal into steps, checking progress, and recovering from errors.

Strip away the branding and every agent framework — LangGraph, CrewAI, the OpenAI Agents SDK, Claude's tool-use loop — reduces to this cycle:

```text
while not done:
    observation = environment.get_state()
    action = llm.decide(goal, memory, observation, available_tools)
    result = tools.execute(action)
    memory.update(action, result)
```

The model never "runs" anything. It *proposes*, the runtime executes, and the result is fed back as new input. Everything impressive about agents lives in the quality of that feedback loop — and everything fragile does too.

## Why now?

Three curves crossed at once:

- **Long context.** Models went from 4k tokens to millions. A whole repository, incident timeline, or legal corpus now fits beside the prompt.
- **Reliable tool use.** Structured outputs and function calling stopped being coin flips. A model that calls the right API 99 times out of 100 is automatable; one that succeeds 70 percent of the time is a toy.
- **Cheap tokens.** Agentic workflows burn thousands of calls per task. At 2021 prices that was absurd. Today it is a rounding error on most engineering budgets.

None of these trends required a research breakthrough. That is why the deployment curve looks vertical: the bottleneck was infrastructure, not intelligence.

## Where agents actually break

<Callout variant="warning" title="The reliability cliff">
An agent that succeeds 90 percent of the time per step fails a twenty-step task 88 percent of the time. Compounding error is the core engineering problem of agentic systems — not model quality.
</Callout>

In production deployments we have reviewed, the failure modes repeat remarkably often:

### 1. Context rot

Long tasks accumulate stale assumptions. The agent "remembers" a file it deleted ten steps ago and keeps patching it. The fix is unglamorous: aggressive state re-grounding, checkpoint summaries, and forcing re-reads before writes.

### 2. Tool sprawl

Every tool you add multiplies the decision space. Teams ship forty tools, watch success rates collapse, then cut to six and watch them recover. Design tool APIs like you design public APIs: small surface, clear contracts, composable.

### 3. Silent drift

Non-deterministic systems need evals, not vibes. Teams that treat agent runs like unit tests — fixed scenarios, scored outcomes, regression tracking on every prompt change — ship reliably. Teams that eyeball three runs do not.

```python
# Minimal eval harness pattern: score every change against a frozen suite
EVAL_CASES = load_cases("evals/agent_tasks.yaml")

def evaluate(agent, cases=EVAL_CASES):
    results = [run_and_score(agent, case) for case in cases]
    report = summarize(results)
    if report.success_rate < THRESHOLD:
        raise RegressionError(report.worst_cases)
    return report
```

## What this means for developers

The uncomfortable truth: agents are currently best at exactly the work junior engineers cut their teeth on — well-specified, sandboxed, verifiable tasks. That does not make senior engineers obsolete; it moves the entry ramp.

The skills that appreciate:

- **Specification writing.** Agents amplify the quality of your problem statement. Vague ticket, vague automation.
- **Systems design.** Someone has to own the loop: tools, permissions, retries, observability, blast radius.
- **Verification engineering.** Tests, evals, and type systems become the guardrails that make autonomy safe. The better your checks, the more you can delegate.

> The developers who thrive with agents will not be the ones who resist them or worship them. They will be the ones who treat them like a powerful, unreliable intern with perfect recall and zero judgment — and build the supervision accordingly.

## The near future

Expect three developments to mature quickly:

1. **Agent-native infrastructure** — sandboxes, permission brokers, and audit trails as standard platform services rather than DIY glue.
2. **Multi-agent patterns with real division of labor**, where planner, implementer, and reviewer roles keep each other honest.
3. **Evaluation as a first-class CI stage**, the same way linting and tests became non-negotiable.

The teams treating agents as a platform concern — versioned, evaluated, observable — are already shipping them to production. The rest are still arguing about whether to allow one in Slack.

Both groups will be surprised by 2027. One of them will be pleasantly surprised.
